# 0003 — Pluggable table specs, with a baseline spec as the default

- **Status:** Proposed
- **Date:** 2026-10-26
- **Plan (if any):** [`docs/plans/2026-10-20-design.md`](../plans/2026-10-20-design.md) §3, §7.2, §9; amends
  [ADR 0002](0002-independent-tool-versioning.md)

## Context

Until now the tool wrote one table spec: the 22 tables of ClinVar-GKM's published latest set (`spec/1.0/`),
whose typed columns follow BigQuery's export so the oracle can compare them. That spec is large, tied to one
consumer's layout, and every typed column needs a SQL template and a spec bump when a record's fields change.
Users also want tables shaped for their own queries. The maintainer decided on 2026-10-26 that:

1. users can pass their own table-spec file (`tables.yaml` in the tool's spec format), and today's 22-table spec
   becomes the built-in spec named `clinvar-gkm`, version 1.0;
2. with no spec named, the tool writes a built-in `baseline` spec: one table per bundle section;
3. the `schema_version` gate stays as it is in every mode.

## Decision

1. **A spec has a name and a version.** Every spec file has a top-level `name` (lower case letters and digits,
   joined by single hyphens) next to `spec_version`. The tool ships two built-in specs, `baseline` 1.0 and
   `clinvar-gkm` 1.0. `--spec` takes a built-in name, alone or with its version (`clinvar-gkm`,
   `clinvar-gkm-1.0`, `clinvar-gkm@1.0`), or else the path of a `tables.yaml`. No `--spec` means `baseline`.
2. **A custom spec goes through the same strict loader and rules** (`src/clinvar_gkm_parquet/spec.py`
   `check_rules`): unknown keys fail; only sections of the accepted bundle `schema_version`s; exactly one `key`
   and one `record` column per table, which the build's self-checks compare with the bundle's key and record; a
   sort key that is the key column, or one whose uniqueness the table documents in `sort_key_unique` (the build
   still checks it); a renderer for every table. A custom spec may not take a built-in's name. Every column still
   cites its bundle path and transform ([ADR 0001](0001-parquet-derived-from-bundles.md)).
3. **The baseline spec** (`spec/baseline/1.0/tables.yaml`, generated by `scripts/make-baseline-spec.py`) has one
   table per section of the 1.1.0 bundle (20), each written to `<section>.parquet`, sorted by `id`, with the
   writer settings of `clinvar-gkm` 1.0 (snappy, row groups of 122,880), and exactly three columns:
   - `id VARCHAR`: the bundle key;
   - `refs STRUCT(path VARCHAR, section VARCHAR, id VARCHAR)[]`: every `#/<section>/<id>` pointer string in the
     record, in document order, `[]` when there is none (derivation kind `refs`);
   - `data JSON`: the bundle record, byte for byte.

   `src/clinvar_gkm_parquet/baseline.py` renders it, under the same contract as the template renderer: one
   SELECT over `bundle_<section>(key, record)`.
4. **`refs` rules.** A pointer is any JSON string value whose text starts `#/`; one that doesn't match
   `^#/[^/]+/.` stops the build, naming the table, key and path. `section` is the text between the first two `/`,
   `id` the rest. `path` is the string's position from the record root: keys joined by `.`, each array position
   written `[]` (`contributions[].contributor`, `members[]`, `extensions[].value[].gene`). A key that is empty
   or holds `.`, `[`, `]`, `"` or `\` is written as a JSON string (`extensions[]."a.b"`), so each path parses
   back to one list of keys. DuckDB's `json_tree` numbers nodes in document order, and the list follows that
   order. Its `fullkey` doesn't quote keys, so it is used only for records with no such key; a record with one
   has its paths built key by key from `json_tree`'s parent links.
5. **`data` is typed `JSON`.** Measured with DuckDB 1.5.4 (2026-10-26): `CAST(record AS JSON)` keeps the bytes
   (no reformatting, escapes kept); `COPY ... (FORMAT parquet)` writes the column with Parquet's JSON logical
   type, and `read_parquet` reads it back as `JSON` with the same bytes. `hash` and `md5` of the JSON value equal
   those of the VARCHAR record, so the build's self-checks pass unchanged.
6. **The version gate stays.** Every spec lists its bundle `schema_version`s; the tool refuses a bundle whose
   version it doesn't accept, and a bundle section the schema doesn't have, whatever spec is used.
7. **The default changes.** A build with no `--spec` writes `baseline`. ClinVar-GKM's release build, the oracle
   and any build meant to match the published set must pass `--spec clinvar-gkm-1.0` explicitly.
8. **Amends ADR 0002 (naming and versioning).** Each spec is versioned on its own (`MAJOR.MINOR`, the bump rules
   of `.claude/rules/table-spec.md`). The compatibility matrix lists, per tool release, each built-in spec with
   its version and marks the default; `version --json` gives the same as `table_specs` (its older
   `table_spec_version`, `table_spec_status` and `tables` keys keep describing `clinvar-gkm`). Each Parquet
   file's key-value metadata names the spec: `clinvar_gkm_parquet.table_spec` (name) and
   `clinvar_gkm_parquet.table_spec_version`; for a custom spec also `clinvar_gkm_parquet.table_spec_builtin`
   (`false`) and `clinvar_gkm_parquet.table_spec_sha256` (of the file's bytes), because a custom file's name and
   version are only what the file says. Output of a custom spec is never the published set.

## Consequences

- **Why `refs` is one fixed list column.** Per-path columns (`location_id`, `proposition_id`, …) differ by section
  and change when a record gains or moves a pointer, which would make the baseline a schema per section and a
  spec bump per bundle change. One `refs` list has the same type in every table and every release. Pointers are
  also polymorphic (a variation's `members[]` names alleles, copy-number counts or changes; a proposition's
  `object` names a condition, a condition set or a therapy group), so a typed column per path would need a
  section column beside it anyway; `refs` carries it in each element. A join from any record to what it points
  at is `UNNEST(refs)` and a match on `section` and `id`.
- **Why `data` stays verbatim.** It is the bundle record (ADR 0001): a user can check it against the bundle by
  bytes, and every field the spec doesn't type is still there to query with DuckDB's JSON functions. Typing it
  `JSON` rather than `VARCHAR` tells Parquet readers what it holds without changing a byte.
- **Why the gate stays.** The tool claims only what it has been run on (ADR 0002). A baseline that accepted any
  bundle would silently read a schema it was never tested on; the cost of a tool release per bundle version
  stays deliberate.
- **Default change.** Anyone who built the published layout without `--spec` gets the baseline after this
  change. ClinVar-GKM's release script, the oracle and parity builds must name `clinvar-gkm-1.0`. The build and
  `verify` wiring of `--spec` comes after this ADR's code lands (planned; not yet in the CLI).
- **Custom specs are limited by renderers.** A custom table is rendered by the baseline renderer when its columns
  are only `key`, `record` and `refs` (any names, order or subset), and otherwise by the template renderer,
  which needs a `sql/<table>.sql` the tool ships; a table that fits neither is refused when the spec loads.
  User-supplied SQL is not part of this decision.
- **Performance is not measured yet.** `json_tree` visits every node of every record. Its cost on a full monthly
  bundle is an open item for the first full baseline build.
- **Location.** `clinvar-gkm` 1.0 stays at `spec/1.0/` for now; moving it to `spec/clinvar-gkm/1.0/` is one entry
  in `spec.BUILTIN_DIRS`.
