**Goal.** A downloadable, versioned tool that rebuilds ClinVar-GKM's Parquet tables from published JSON bundles,
for any release, so that (1) users can regenerate Parquet for current and archived releases, and (2) ClinVar-GKM
publishes its latest Parquet set with the same tool and retires its BigQuery Parquet SQL.

---

## 1. Scope

### In scope for v1 (table spec 1.0)

- Reproduce **exactly** the 22 Parquet tables of ClinVar-GKM's latest set in the **1.1.0 layout**: the same
  table names, column names, column order, DuckDB types and values, including the shared proposition schema
  across the four proposition tables.
- Inputs: a full bundle (an official monthly or a weekly full), optionally followed by a chain of weekly delta
  bundles replayed to a later release; from local files or URLs, with checksum verification.
- Output: the 22 table files plus a dataset manifest (§7.3) that ClinVar-GKM publishes beside them.
- Accept bundle `schema_version` **1.1.0** only.
- A CLI with `build`, `verify` and `version --json`.
- The oracle against ClinVar-GKM's BigQuery-exported latest set, table by table.

### Later (not v1)

- The **lookup-file family** planned in ClinVar-GKM PR #151 (`docs/superpowers/plans/2026-10-17-variant-sorted-parquet.md`
  on `main`): `statement-by-variant`, `statement-by-object`, `concept-set-membership`, `variant-gene`,
  `statement-by-gene-context`, and `statement-by-citation` keyed on a typed `citation_id` (`pmid:`, `doi:`,
  `url:`). These arrive as **table spec 1.1** (additive), see [§13](#13-later-spec-versions-the-lookup-files).
- Layout clean-ups that would break consumers (snake_case `condition` columns, `id`/`data` instead of
  `key`/`value` on `therapy` and `therapyGroup`): a future spec 2.0, if wanted.

### Non-goals

- Publishing anything. Uploads to R2, index updates and CDN purges stay in ClinVar-GKM's release scripts.
- Validating bundles against the JSON schema. That is ClinVar-GKM's release gate (gkm-toolkit). The tool checks
  only what it needs: `schema_version`, sections, the line layout, checksums, and record shapes it maps.
- Reading 1.0.x bundles (see [D7](#d7-archived-10x-bundles)).

## 2. Background: what ClinVar-GKM publishes and how Parquet is built today

### 2.1 Published artifacts

From 1.1.0, ClinVar-GKM publishes under the layout of
[ADR 0009](https://github.com/clingen-data-model/clinvar-gkm/blob/docs/adr-0008-bundle-record/docs/decisions/0009-r2-layout-mirrors-ncbi-clinvar.md)
(proposed, PR #168). Base URL `https://data.clinvar-gkm.org`. Each version line has its own folder,
`v{major}/{major}.{minor}/`: 1.1.x releases go in `v1/1.1/`; a new MINOR starts `v1/1.2/`, a new MAJOR `v2/2.0/`.

```text
v1/1.1/
  index.json                                   line index
  clinvar-gkm_YYYY-MM.json.gz (+ .sha256)      official monthlies, current year
  clinvar-gkm_00-latest.json.gz (+ .sha256)    newest official monthly
  weekly/
    clinvar-gkm_YYYY-MMDD.json.gz (+ .sha256)  weekly FULL bundles, current month only
    clinvar-gkm_00-latest_weekly.json.gz       newest weekly full (+ .sha256)
  deltas/
    clinvar-gkm-delta_YYYY-MMDD.json.gz (+ .sha256)
    clinvar-gkm-delta_YYYY-MMDD.manifest.json  delta manifest
    YYYY-MM/                                   earlier months of the current year
  archive/YYYY/                                prior years' monthlies
    deltas/YYYY-MM/                            prior years' deltas
  parquet/
    <table>.parquet                            ONE dataset, overwritten every release
    manifest.json                              build date, source release, tool version
v1/1.0/                                        frozen 1.0.1 generation, no Parquet
```

| Artifact | Where | Facts |
| --- | --- | --- |
| Official monthly full | `v1/1.1/clinvar-gkm_YYYY-MM.json.gz`, alias `clinvar-gkm_00-latest.json.gz` | One gzip JSON object; the 1.0.1 2026-10 full is 4,832,959,259 bytes (verified 2026-10-20). Built from the last weekly release before ClinVar's monthly cut ([ClinVar-GKM ADR 0002](https://github.com/clingen-data-model/clinvar-gkm/blob/main/docs/decisions/0002-monthly-full-anchored-to-clinvar-index.md)), e.g. 2026-10 ← 2026-09-28. The line index gives each monthly's `sha256` and **`source_release`** (the release it was built from) |
| Weekly full | `v1/1.1/weekly/clinvar-gkm_YYYY-MMDD.json.gz`, alias `clinvar-gkm_00-latest_weekly.json.gz` | **New in 1.1.0:** a full bundle for every weekly release. Only the current month's are kept; they are **deleted** when the first release of the next month posts |
| Weekly delta | `v1/1.1/deltas/clinvar-gkm-delta_YYYY-MMDD.json.gz` + manifest; earlier months in `deltas/YYYY-MM/` | Same shape as a full, holding only added and updated records; deletes are listed only in the manifest. The 1.0.1 2026-10-11 delta is 10,754,403 bytes. Each manifest's `checkpoint_full` names the official monthly that **precedes** the delta |
| Checksums | `<file>.sha256` sidecar (`sha256sum -c` format) next to every bundle, and `sha256` fields in the line index | **From 1.1.0.** The live 1.0.1 files have no sidecars |
| Prior-year archive | `v1/1.1/archive/YYYY/` (monthlies) and `archive/YYYY/deltas/YYYY-MM/` | Moved there when the first release of a new year posts. A move keeps the file's bytes, name and sha256 |
| Frozen line | `v1/1.0/` | The 1.0.1 generation, first copied to `archive/1.0.1/` on 2026-10-18 (40 objects, 24,297,367,494 bytes), then moved here. A frozen line keeps its `MANIFEST.json` (size + sha256 per file) and `README.txt`, and has **no Parquet** |
| Parquet | `v1/1.1/parquet/<table>.parquet` + a manifest file | **One dataset**, rebuilt from the newest release and overwritten every release. The manifest states the build date, source release and tool version and replaces the old `source.json`; this tool writes it (§7.3), and for 1.1.0 the BigQuery export does. No Parquet anywhere else: not per month, per delta, in `archive/` or in frozen lines. Past Parquet is rebuilt from the bundles with this tool |

**Paths move; bytes don't.** A delta's URL changes at month rollover and a monthly's at year rollover. Scripts
resolve paths through the line index, not hard-coded URLs (§4.1).

**Before 1.1.0** (the live 1.0.1 site on 2026-10-20): monthlies in `v1/datasets/`, each delta in its own
`v1/deltas/<YYYY-MMDD>/` folder with a `manifest.json`, dated Parquet sets under `v1/datasets/parquet/` with a
`00-latest/` set and `source.json`, and the copy at `archive/1.0.1/`. ADR 0009 moves `archive/1.0.1/` to
`v1/1.0/` and deletes the rest once the new layout is live.

### 2.2 How the latest Parquet set is built today (1.1.0)

`release-gkm-parquet.sh` (on `1.0`), called by `run-release.sh` after each weekly delta:

1. `export-gkm-dicts.sh --parquet-only` runs one BigQuery `EXPORT DATA` per table over the **full** `gkm_dict_*`
   tables of the newest dataset, using `src/scripts/parquet-schemas/*.sql` (19 files; `proposition.sql` is
   run once per proposition section, giving 22 tables). Three temp UDFs are prepended: `is_blank`,
   `collapse_ext_values` (JS) and `bundle_cleanup` (JS port of the assembler's `strip_empty` + value collapse).
2. Shards are downloaded and merged per table with DuckDB 1.5.4 (`COMPRESSION SNAPPY`, default row groups).
3. Upload the files, write `source.json`, delete stale table files. (The `1.0` code uploads to the old
   `v1/datasets/parquet/00-latest/`; under ADR 0009 the target is `v1/1.1/parquet/` and a manifest file replaces
   `source.json`.)

The set is about 12 GB (the script's own comment). On the live 1.0.1 set, the files carry no Parquet key-value
metadata (`parquet_kv_metadata` is empty), `created_by` is DuckDB 1.5.4, and `allele.parquet` has 37 row groups
for 4,554,562 rows, the DuckDB default of 122,880 rows per group. They are not sorted by id: ClinVar-GKM measured
every one of `scv.parquet`'s 55 row groups spanning the full SCV id range (2026-10-15).

The bundle, by contrast, is written by `assemble-gkm-dicts.py`, which runs every record through
`gkm_json_cleanup.py` (`strip_empty`, then `collapse_ext_values`). So the Parquet SQL re-derives each table in
parallel to the bundle and has to mirror the cleanup: the defect class ClinVar-GKM ADR 0007 Workstream 1 targets.

## 3. Table spec v1 (spec 1.0)

### 3.1 Where the authoritative spec lives

- **In this repo, versioned:** `spec/1.0/tables.yaml` (machine-readable contract) and `spec/1.0/README.md`
  (generated, human-readable). One directory per spec version; a released directory is never edited
  (`.claude/rules/table-spec.md`).
- **Per table:** output file name; source bundle section(s); row filter; sort key; and per column: name, exact
  DuckDB type string (including nested struct field order), empty-versus-NULL rule, derivation (bundle JSON
  path + transform), and a one-line description.
- **Extension slot map:** for each typed `extensions` column, the mapping from extension `name` to the typed
  slot that holds its value (`value_string`, `value_boolean`, `value_coding`, `value_hgvs_array`,
  `value_gene_array`, `value_submitted_condition_set`, `value_submitted_condition`, …). An extension name the
  map doesn't list stops the build.
- **Implementation:** one DuckDB SQL file per table under `src/clinvar_gkm_parquet/sql/`. A test builds each
  table on the fixtures and asserts `DESCRIBE` equals the spec exactly.

**How ClinVar-GKM's docs reference it** (recommended; [D5](#d5-who-owns-column-descriptions)): the Ecosystem
add-on page links to `spec/<version>/README.md` at the tag of the tool version ClinVar-GKM pins. The column
reference `docs/parquet/tables.md` keeps its teaching prose but states which spec version it describes and
links to the spec as the authority for names and types. Its "Full nested types" blocks (today pasted from
`DESCRIBE`, with a `<!-- regenerate after 1.1.0 export -->` marker) are regenerated from the spec rather than
maintained by hand.

### 3.2 How spec 1.0 is derived

Spec 1.0 is **captured from the first published 1.1.0 latest set**, not written from docs: `DESCRIBE` of all 22
files gives names, order and types; a scan of every `extensions` column gives the slot map. It is then
cross-checked against the 1.1.0 column reference (`docs/parquet/tables.md` on PR #146) and the 19 SQL files on
`1.0`. Capturing from the export matters because the 1.1.0 set doesn't exist yet: the docs are written ahead of
it, and the docs page still shows several 1.0.1 numbers.

### 3.4 Kinds of derivation

Every column is one of these, and the spec says which:

| Kind | Example | Rule |
| --- | --- | --- |
| Record | `data`, `therapy.value` | The bundle record, byte for byte as it appears on its bundle line |
| Scalar path | `allele.name`, `copyNumberCount.copies` | One JSON path, cast to the spec type (`BIGINT` for counts and coordinates) |
| Bare id | `allele.location_id`, `scv.proposition_id`, list elements of `has_evidence_lines` | A `#/<section>/<id>` pointer with `^#/[^/]+/` removed |
| Pointer section | `scv.proposition_section`, proposition `object_type` | The `<section>` part of a pointer. A non-pointer `object` stops the build, as `proposition.sql` does with `ERROR()` |
| Typed copy | `scv.classification`, `variation.mappings`, `condition.primaryCoding` | The record field cast to the spec's nested type: struct fields by name, absent fields NULL |
| Extension slot | `scv.extensions`, `variation.extensions` | Each extension `{name, value}` becomes `{name, value_<slot>: value}` using the slot map |
| Computed | `loc_start_min`, `gene_context_id`, `gene_context_source`, `submitted_gene_symbols` | A documented function of record fields, ported from the SQL file (e.g. `gene_context_id` is `ncbigene:` prefixed to `geneContextQualifier.primaryCoding.code`) |

### 3.5 The hard parts (where exact parity is at risk)

These come from the struct-typed tables (`variation`, `condition`, `conditionSet`, `evidenceLine`,
`vcv_evidenceLine`, `rcv_evidenceLine`, `scv`, `vcv`, `rcv`), whose typed columns are BigQuery's own table
columns (`SELECT t.*`), not explicit JSON extractions:

1. **Nested types aren't derivable from one record.** Field order, integer widths and which fields a struct has
   are properties of the schema. The spec declares them; the tool casts to them.
2. **Extension values are collapsed in the bundle.** The bundle has `{name, value}`; the typed column has
   `{name, value_string, value_boolean, …}`. The slot map in the spec restores the slot by name.
3. **Empty versus NULL.** BigQuery returns a NULL array as an empty array, so typed list columns from BigQuery
   are expected to be `[]`, never NULL, while the bundle omits empty arrays (`strip_empty`). The spec records
   the rule per column; the oracle confirms it. Scalar-path columns from `JSON_VALUE` are NULL when absent.
4. **All-null structs.** A dict-table struct with only NULL fields is dropped from the bundle by `strip_empty`
   but may survive as a non-NULL struct in the BigQuery typed column. The tool follows the bundle (NULL). Any
   such difference is a BigQuery-side deviation from the bundle (ADR 0001) and is listed in the oracle report.
5. **Type conversions.** `scv.contributions.date` is `DATE` (bundle: `"YYYY-MM-DD"` string);
   `variation.constraints.copies` and `extensions.value_coding` are `BIGINT`.
6. **`data` bytes.** The tool's `data` is the bundle record verbatim. BigQuery's `data` is produced by a JS
   `JSON.stringify` (or `JSON_STRIP_NULLS` + collapse for struct tables), so key order, number formatting or a
   latent `[{}]` element (ClinVar-GKM simplification plan §9.3) could differ. The oracle compares bytes first
   and parsed JSON second, and reports both.

## 4. Inputs

### 4.1 Sources and checksums

- **Local path or URL** for every input file. URLs are fetched with `User-Agent: clinvar-gkm-parquet/<version>`,
  one stream per file, with retry and `Range` resume.
- **Checksum sources**, in order: an explicit `--sha256`; the `<file>.sha256` sidecar next to the file (local or
  remote); the `sha256` in the line index (`v1/1.1/index.json`, provisional path) for that file; the `sha256` in
  a frozen line's `MANIFEST.json`. The sha256 of the compressed bytes is computed while streaming. A mismatch
  stops the build. No checksum available (e.g. a 1.0.1 file): the build continues, records the computed sha256,
  and warns.
- **Aliases.** `clinvar-gkm_00-latest` and `clinvar-gkm_00-latest_weekly` are resolved through the line index to
  the dated file with the same size and sha256, and the dated name is recorded, so provenance doesn't point at a
  moving alias.
- **Moving paths.** A delta moves into `deltas/YYYY-MM/` at month rollover, a monthly into `archive/YYYY/` at year
  rollover, and a weekly full is deleted at month rollover. The tool finds files by release through the line
  index, never by a hard-coded path. A `checkpoint_full.path` in an older delta manifest can name a monthly's
  pre-move location; the tool resolves it by its release.
- **`--release latest|YYYY-MM-DD`** (convenience): resolve the inputs from the line index. For the newest
  release, or any week still in `weekly/`, the input is that weekly full, with no replay. For an earlier week,
  the input is a monthly plus deltas, chosen by the replay rule in §4.3.
- **The line index shape** (`r2_layout.build_index` @ `25344ba`): top-level `base_url`, `latest_release`,
  `datasets` (`monthly[]`, `weekly[]`), `deltas[]` and `archives{YYYY: {monthly, deltas}}`. A monthly entry has
  `release` = its `YYYY-MM` label and a separate `source_release`; the aliases are entries with `latest: true`. A
  delta entry is `{release, month, path (its folder), manifest, bundle: {path, sha256, size}}`, so its checksum
  is `bundle.sha256`. At month rollover the finished month's newest weekly full stays until the new monthly is
  posted, so `weekly[]` can hold one weekly from the previous month.

### 4.2 The bundle line format (verified)

From `assemble-gkm-dicts.py` on `1.0` (`assemble()`), and confirmed on the first 300 KB of the live 2026-10-11
delta bundle:

```text
{
  "schema_version": "1.1.0",
  "sequenceReference": {
    "<key>": <record>,
    ...
    "<key>": <record>
  },
  "location": {
  ...
  }
}
```

- Line 1 is `{`; line 2 is `"schema_version": "<v>",` indented two spaces. The assembler always writes it first.
  A bundle with no sections (a zero-change delta) has no comma after it, and line 3 is `}`.
- A section opens with `"<section>": {` and closes with `}` (followed by `,` unless it is the last section),
  both indented two spaces. Sections appear in the assembler's `SECTIONS` order; an empty section is omitted
  entirely (it is opened lazily, on its first record).
- Each record is exactly one line: four spaces, the JSON-encoded key, a colon and a space, the compact JSON
  record, and a trailing `,` on every record but the section's last. Keys and records are serialized by
  `orjson` (or the stdlib fallback), which never emits a raw newline, so one record per line holds.
- The 1.1.0 sections are the 20 in the bundle schema (`schema/clinvar-gkm/clinvar-gkm-bundle.schema.json` @
  `1.0`, `$id` `…/clinvar-gkm/1.1.0/json/ClinvarGkmBundle`): `sequenceReference, location, allele,
  copyNumberCount, copyNumberChange, gene, variation, condition, conditionSet, therapy, therapyGroup,
  submitter, propositionPathogenicity, propositionOncogenicity, propositionSomaticClinicalImpact,
  propositionClinvarCustom, evidenceLine, scv, vcv, rcv`.

The reader parses each record line with a strict grammar and fails on anything else (a line it can't classify,
a duplicate key within a section, an unknown section). This layout is an implementation detail of the assembler,
not a schema guarantee; see [D4](#d4-is-the-one-record-per-line-layout-a-contract).

### 4.3 Delta replay

The model, from ClinVar-GKM `docs/data-access/release-model.md` and `weekly-deltas.md` (PR #146):

- A consumer reaches a later state by taking an official monthly and replaying the weekly deltas after it,
  oldest first. For each delta: apply the manifest's `deleted` keys per section, then upsert every record in the
  delta bundle per section.
- **The replay rule** (ClinVar-GKM ADR 0009 §4). To rebuild week W:
  1. take the newest official monthly whose `source_release` ≤ W (from the line index);
  2. apply, in release order, every delta whose `release` is later than that `source_release` and ≤ W;
  3. check the chain: the first delta's `baseline_release` equals the monthly's `source_release`, and each later
     delta's `baseline_release` equals the previous delta's `release`. A gap means a missing week.
- Each delta manifest's `checkpoint_full` names the official monthly that precedes the delta, so a manifest on
  its own also says where its chain can start. Its shape in the code (`r2_layout.py` @ `25344ba`) is
  `{path, release, month, sha256}`, where `release` is the monthly's **source release** and `month` its
  `YYYY-MM` label. (ClinVar-GKM's `weekly-deltas.md` on `1.0` still shows the old `{path, release: "YYYY-MM"}`.)
- A 1.1.0 manifest also carries the delta bundle's `sha256`, `bundle {name, path, size, sha256}` and
  `schema_version`; the tool checks the staged delta against them.
- A delete of a key that isn't in the prior state is a no-op with a warning, as in ClinVar-GKM's own replay
  example and delta-reconstruction oracle.
- If W is still in `weekly/` (the current month), its weekly full is the same state with no replay.
- Delta manifests list sections by bundle section name (in 1.1.0, the proposition sections are named by
  `gkm_proposition_section`, see `build-delta-manifest.py`); VCV and RCV evidence-line changes are listed under
  `evidenceLine`.

**Two problems found while checking the 1.0.1 data, and their status:**

1. **`checkpoint_full` couldn't tell you where to start. Fixed in ClinVar-GKM ADR 0009.** On the live 1.0.1
   manifests, *every* delta from 2026-07-06 to 2026-10-11 had `checkpoint_full` = the 2026-10 monthly, because the
   field was filled "from current R2 monthly state" at upload (`build-delta-manifest.py`) and the republish
   re-uploaded every delta after the 2026-10 full existed. Nothing machine-readable said which release a monthly
   was built from (2026-10 ← 2026-09-28 was only in the docs prose; 2026-08 ← 2026-08-04 is not month-aligned).
   From 1.1.0, each `checkpoint_full` names the monthly that precedes the delta, and the line index publishes
   each monthly's `source_release`. See [D3](#d3-the-monthly-fulls-source-release-isnt-machine-readable).
2. **The docs' Python replay example skipped the deltas it needs.** It kept deltas with
   `release[:7] > checkpoint_month`. With the 2026-10 full (from 2026-09-28) that drops 2026-10-04 and
   2026-10-11, and returns the 2026-09-28 state. ADR 0009 records the defect and states the correct rule (above);
   the docs fix is ClinVar-GKM's.

**How the tool replays** (no in-memory dict of 90 M records):

1. Stage the full and each delta as per-section `(key, record, seq)` rows, where `seq` is 0 for the full and
   `i` for the i-th delta. Stage each manifest's deletes as `(section, key, seq, tombstone)`.
2. Check the chain: the first delta's `baseline_release` equals the monthly's `source_release`; each later
   `baseline_release` equals the previous delta's `release`. Fail otherwise.
3. Per section, the final state is: for every key, the row with the highest `seq`, dropped if that row is a
   tombstone. Within one delta, deletes apply before upserts, so an upsert of a key deleted in the same delta
   wins. In SQL this is a `QUALIFY row_number() OVER (PARTITION BY key ORDER BY seq DESC, is_upsert DESC) = 1`
   over a small "touched keys" set unioned with the untouched full rows.
4. Record each input's release and sha256 in the output metadata.

Replay starts from the newest monthly whose `source_release` ≤ the target, so the known cross-version allele
shift between 2026-08-22 and 2026-08-29 (ClinVar-GKM `docs/reference/known-issues.md`; simplification plan §9.4)
is not crossed for any target from 2026-08-29 on: the 2026-09 monthly is built from 2026-08-29 (maintainer
notes, §15).

### 4.4 `schema_version`

The reader takes `schema_version` from line 2. Missing, or not in the tool's accepted list: stop with an error
that names the accepted versions and the compatibility matrix. Every input in a replay chain must have the same
`schema_version`.

## 5. Streaming reader

- Pure Python, stdlib `gzip` + `hashlib`, `orjson` when installed. One pass per input file: decompress, hash the
  compressed stream, classify lines, write staging files.
- Staging format (recommended): per section, gzip (level 1) text files with one `key<TAB>record` per line. JSON
  text contains no raw tab or newline, so the split is unambiguous; DuckDB reads these with `read_csv`
  (`delim='\t'`, `quote=''`, `escape=''`, two `VARCHAR` columns) in parallel across sections. Alternative if
  this proves slow: write staging Parquet via `pyarrow` (one more dependency).
- The key stays JSON-encoded in staging (so it can't hold a raw tab) and is decoded in SQL; the record is kept
  as the exact bytes from the line, so `data` is byte-identical to the bundle.
- Throughput: a monthly full is about 26 GB of JSON text (the delta sample compressed about 5.5 : 1) and about
  90 M record lines. Measured on the maintainer's laptop (2026-10-20) on a 201 MB, 364 K-line input made from
  the fixture's real lines: staging at about 175 MB/s (0.32 M lines/s, single-threaded; about half is the
  level-1 gzip of the staging output), and the DuckDB load at about 0.85 M rows/s. Extrapolated to a monthly
  full: about 2.5–5 minutes for staging (an estimate; a real full has shorter lines on average, about 290 bytes
  against the fixture's 550). Not yet measured on a real full (§12 step 1).
- Duplicate keys within a section are detected when the staged section is loaded into DuckDB, not while
  streaming (a Python set for 27 M keys would cost 2–3 GB of memory).

## 6. Engine: DuckDB

### 6.1 Why DuckDB

- It is already a ClinVar-GKM release dependency (DuckDB 1.5.4 merges the Parquet shards today), and the
  published files are written by it, so writer behaviour (row groups, encodings) matches.
- Its JSON functions, explicit `STRUCT`/`LIST` casts and `QUALIFY` express every derivation in §3.4 as SQL
  close to today's BigQuery files, which keeps the port reviewable side by side.
- It spills to disk under a memory limit, so a 90 M-row build runs on a workstation.
- `COPY … TO … (FORMAT parquet, KV_METADATA {...})` writes the required per-file metadata.

Considered and not chosen: pyarrow-only (every derivation hand-written in Python), Polars (no clear gain, a
second engine for ClinVar-GKM), BigQuery reload (needs credentials; users can't run it).

### 6.2 Build stages

1. **Stage** (§5): bundles → per-section staging files; checksums; `schema_version`; chain check.
2. **Replay** (§4.3, only with deltas): per section, resolve the final `(key, record)` set into a DuckDB table.
3. **Tables**: run each table's SQL over its section, casting to the spec types, then
   `COPY (… ORDER BY <sort key>) TO '<out>/<table>.parquet'` with the spec's writer settings and metadata.
   Tables are built one at a time, largest last, so a failure is cheap and disk peaks stay bounded.
4. **Self-check**: `DESCRIBE` equals the spec; row count equals the section's key count (after the
   evidence-line split); `data` ids equal keys.

### 6.3 Memory and disk budget (estimates, to measure in v0)

| Item | Size |
| --- | --- |
| Input monthly full (if downloaded rather than streamed) | 4.8 GB |
| Staging files (gzip level 1, about 26 GB of JSON) | about 5–8 GB |
| DuckDB working database for replay and the largest table (`propositionPathogenicity`, 27.4 M rows) | several GB, spilling to `--work-dir` |
| Output set (same compression as today) | about 12 GB |
| **Peak free disk needed** | **about 30–40 GB; recommend 50 GB** |
| Memory | `--memory-limit` (default: DuckDB's 80 % of RAM); 16 GB RAM recommended, 8 GB should work with spilling |

The maintainer's workstation had about 14 GB free on 2026-10-20 (`df`), and ClinVar-GKM's notes put the build
machine at about 15 GB free. Neither fits a full build plus the oracle's reference set, so the oracle and the
ClinVar-GKM release build need a machine with more disk ([D9](#d9-where-the-oracle-and-the-release-build-run)).
`--tables` builds a subset, and each section's staging file is deleted once every table that reads it is built,
unless `--keep-work`.

## 7. Output

### 7.1 Files and writer settings (spec 1.0)

- One file per table, `<table>.parquet`, the same names as today's latest set.
- Writer settings for parity with the published set: `COMPRESSION snappy`, `ROW_GROUP_SIZE 122880`, no bloom
  filters. Sort by the table's id column (`id`, or `key` for `therapy`/`therapyGroup`), which makes the build
  deterministic and makes row-group `id` statistics selective, so a remote lookup by id reads one row group
  instead of all of them. Row order is not part of the oracle comparison.
  ([D10](#d10-compression-and-sort-order-for-the-core-tables))

### 7.2 Key-value metadata (every file)

| Key | Example |
| --- | --- |
| `clinvar_gkm_parquet.tool_version` | `0.1.0` |
| `clinvar_gkm_parquet.table_spec_version` | `1.0` |
| `clinvar_gkm_parquet.table` | `scv` |
| `clinvar_gkm_parquet.bundle_schema_version` | `1.1.0` |
| `clinvar_gkm_parquet.source_bundle_sha256` | the full's sha256 (hex) |
| `clinvar_gkm_parquet.source_deltas` | JSON array of `{release, sha256}`, oldest first; `[]` for a full-only build |
| `clinvar_gkm_parquet.source_release` | the release the output represents: the last delta's `release`; with no deltas, a monthly's `source_release` or a weekly full's own release |
| `clinvar_gkm_parquet.duckdb_version` | `1.5.4` |

No timestamps in Parquet metadata, so the same inputs give byte-identical files and a rebuild can be checked
with `sha256sum`. Measured with DuckDB 1.5.4 (2026-10-20): files are byte-identical across runs, across 1, 4
and 8 threads, with `preserve_insertion_order` on or off, and with the sort spilling to disk. This holds because
every sort key is unique, so the build fails if one isn't.

### 7.3 The dataset manifest

The tool **writes the dataset manifest** next to the files, as `manifest.json`, the name ClinVar-GKM's layout
code uses (`parquet/manifest.json` in `r2_layout.py` @ `25344ba`).
ClinVar-GKM publishes it unchanged at `v1/1.1/parquet/` beside the tables, where it replaces the old
`source.json`. It holds:

- what ADR 0009 requires: the **build date**, the **source release** (§7.2 `source_release`) and the **tool
  version**;
- everything else in §7.2: table-spec version, bundle `schema_version`, DuckDB version, the source full and
  deltas with their releases and sha256s;
- input URLs or paths and sizes, per-table row counts and file sha256s, and build start and end times;
- the label "derived from the bundle; may be regenerated" (ClinVar-GKM ADR 0008 (e)).

It covers the fields of the old `source.json` (`derived`, `note`, `release`, `schema_version`, `sections`;
`generated_at`), and it is a superset of the manifest ClinVar-GKM's own `r2_layout.py parquet-manifest` writes
(`builder`, `dataset`, `files: [{name, size, sha256}]`, `table_spec_version`), whose fields `build_index` copies
into the line index. `dataset` (a BigQuery dataset name) is not something the tool can know, so it is `null`. The manifest carries timestamps and is not byte-reproducible; the Parquet files are (§7.2).

## 8. Testing

### 8.1 Unit tests

- **Fixtures from real bundles.** A checked-in script streams published bundles and extracts a small connected
  excerpt: a few dozen variations chosen to cover the shapes (allele, copy-number count and change, uncertain
  range locations, haplotype members, a germline and a somatic VCV, an RCV, SCVs with each extension slot, a
  therapy group, a gene-context placeholder, a `hgvs` repair extension), plus every record they reference. It
  writes a mini-bundle in the exact line format, with a header recording the source URLs, releases,
  `schema_version` and source sha256s. Target under 1 MB, committed.
  **Until a 1.1.0 bundle can be read** (none is published, and the maintainer's laptop has no disk to stage
  one), the tests use a **provisional** fixture, `tests/fixtures/examples-1.1.0/`: the 42 records of
  ClinVar-GKM's `examples/` (`origin/1.0` @ `25344ba`, built from `clinvar_2026_10_04_v2_6_0`), de-inlined back
  into 346 records in the exact line format by `scripts/make-example-fixtures.py`. Re-inlining them gives back
  every example exactly. It is not bundle bytes (record keys are in alphabetical order), it predates parts of
  the 1.1.0 code (no `geneContextSource` extension; `vcv-` condition-set members as bare CURIEs), and it has no
  copy-number, therapy-group, haplotype, uncertain-range, gene-context-placeholder or `hgvs`-repair records.
  It is replaced by a real excerpt once the 2026-10-18 1.1.0 bundle is available.
- **Golden rows from the real export, same release.** The latest Parquet set represents a weekly release that
  has no published full, so fixture and golden rows are both taken at the oracle's release (§8.2): records from
  the replayed state (the published full plus its deltas), and expected rows for the same ids from the frozen
  BigQuery reference set, saved as JSON. Tests compare the tool's rows with them, column by column.
- **Replay fixtures** from real deltas: keys added, updated and deleted in the 2026-10-04 and 2026-10-11 (or
  their 1.1.0 equivalents) manifests, plus a synthetic broken chain and a delete-then-add case.
- **Negative controls:** an unknown `schema_version`, an unknown section, an unknown extension name, a malformed
  line, a checksum mismatch, a non-pointer proposition `object`. Each must fail with a clear message.
- **Determinism:** build the fixtures twice; file sha256s match.

### 8.2 The oracle

Compares the tool's output with ClinVar-GKM's **BigQuery-exported latest set for the same release**, table by
table. It is the switch-over gate.

**Reference.** The BigQuery set is overwritten every weekly release, so the oracle needs a frozen copy: the
22 files plus their manifest file (`source.json` in the `1.0` code), with their sha256s, taken right after a
publish (or kept from `release-gkm-parquet.sh --no-upload` staging). The 1.1.0 republish is the first chance:
ClinVar-GKM's 1.1.0 rebuild runbook (PR #180, draft, §4.7) stages exactly the pair the oracle needs, the
BigQuery latest Parquet built from **2026-10-18** and a reference 2026-10-18 full bundle that is never
published. Keeping both, with sha256s, after the publish ([D14](#d14-keep-the-110-oracle-reference)) gives the oracle its reference and gives
the replay engine a direct test: replaying the 2026-10 full plus the 2026-10-04, 2026-10-11 and 2026-10-18
deltas must reproduce the reference full, section by section. Under ClinVar-GKM ADR 0009 a weekly full is
published for every release, so a 2026-10-18 full may also sit in `v1/1.1/weekly/` until the November rollover
deletes it; whether it is byte-identical to the runbook's reference full is not verified (§15).

**Inputs for the tool.** By the replay rule (§4.3), from the manifest's source release: for the first 1.1.0
set, the 2026-10 monthly (`source_release` 2026-09-28), then the 2026-10-04, 2026-10-11 and 2026-10-18 deltas.
Where the weekly full of the same release is available, build from it too; both builds must match.

**Prior art to reuse.** The runbook's Appendix A (`toolkit-validate-bundle.py`, a streaming per-record
validator) and Appendix B (`bundle-parquet-check.py`: counts, both-direction id sets, sampled `data` equality,
streaming) already read real bundles line by line; port what fits rather than starting over.

**Per table:**

1. Schema: column names, order and full DuckDB types are identical (string comparison of `DESCRIBE`).
2. Row count equal.
3. Id sets equal, both directions (`EXCEPT`), with counts and a sample of each side.
4. Every typed column: join on id and count rows where `a.col IS DISTINCT FROM b.col`, per column, with samples.
   Nested columns are compared as values; a mismatch is broken down by nested path in the report.
5. `data` (and `therapy`/`therapyGroup` `value`): byte equality; where bytes differ, parsed-JSON equality, so
   the report separates formatting differences from content differences.

**Pass criterion.** Zero unexplained differences. A difference is either fixed in the tool, or listed with its
cause and accepted by the maintainer. A BigQuery-side deviation from the bundle (§3.5 items 3, 4 and 6) is
accepted only with the maintainer's sign-off, because after the switch-over the published Parquet changes to the
bundle-faithful value.

**Second leg (bundle recompute):** for every table, the id set equals the bundle section's keys (after the
evidence-line split), and every `data` equals its bundle record bytes. This doesn't need BigQuery and is the
check `verify --bundle-recompute` runs for any release.

**Implementation.** `clinvar-gkm-parquet verify <out> --against <reference dir>` runs the per-table comparison
and writes a Markdown and JSON report. The same command can serve as ClinVar-GKM's bundle-to-Parquet release
gate (simplification plan §7, check 6).

Run the oracle on at least two releases: the first 1.1.0 latest set, and one more weekly release.

### 8.3 CI (GitHub Actions)

- `ci.yml` on pull requests and `main`: `ruff`, `pytest` on Python 3.10–3.13, Linux and macOS. No network.
- `release.yml` on a version tag: build sdist and wheel, publish to PyPI by trusted publishing (OIDC, no stored
  token), create the GitHub Release from the changelog. A `pypi` environment limited to tags.
- Every workflow declares explicit, minimal `permissions` (ClinVar-GKM moved to read-only default tokens on
  2026-10-18; follow the same rule). No repository secrets.
- The oracle doesn't run in CI: it needs about 50 GB of disk and the frozen reference set. Its reports are
  committed under `docs/oracle/` with the tool version and inputs.

## 9. Versioning, compatibility and packaging

### 9.1 Versions

Per [ADR 0002](../decisions/0002-independent-tool-versioning.md): tool semver; table spec `MAJOR.MINOR`; an
explicit accepted `schema_version` list per tool release.

### 9.2 Compatibility matrix (planned)

| Tool version | Bundle input (`schema_version`) | Table spec | State |
| --- | --- | --- | --- |
| 0.1.x | 1.1.0 | 1.0 | planned: first build, before the oracle |
| 1.0.0 | 1.1.0 | 1.0 | planned: the version ClinVar-GKM first pins, after the oracle passes |
| 1.1.0 | 1.1.0 | 1.1 | planned: adds the lookup files |

The matrix is published in `README.md` and in `version --json`; the `release-tool` skill updates both. The tool
refuses any other `schema_version`. A new bundle version (even a PATCH) needs a tool release that lists it,
after a build and `verify` on a real bundle of that version.

### 9.3 Packaging and distribution

**Recommendation: PyPI, with a matching GitHub Release.** ([D1](#d1-packaging))

- PyPI makes a pinned run one line: `uvx clinvar-gkm-parquet@1.0.0 build …` or `pipx run`. ClinVar-GKM pins the
  same way in its release script. GitHub Releases alone would need a download-and-install step or a
  `git+https` URL pin, which is slower and easier to get wrong.
- The PyPI name `clinvar-gkm-parquet` was free on 2026-10-20 (the JSON API returned 404).
- Publish with PyPI trusted publishing from the release workflow, so no API token is stored.
- Pin `duckdb` exactly (`==`) in each release, because the output bytes depend on it. Install in an isolated
  environment (`uvx`/`pipx`) to avoid clashing with a user's own DuckDB. ([D8](#d8-pin-duckdb-exactly))
- Tags: `vX.Y.Z` (recommended), to tell tool versions apart from bundle schema versions such as `1.1.0`.
  ClinVar-GKM tags have no `v`. ([D6](#d6-tag-format))

## 14. Risks and open decisions

**user** = the maintainer must decide; **default** = the implementer proceeds with the recommendation unless
told otherwise.

### D1. Packaging

**user.** PyPI + GitHub Release (recommended, §9.3) or GitHub Releases only. Needs a PyPI account and a trusted
publisher configured for this repo.

### D2. What ClinVar-GKM feeds the tool

**user. Partly resolved (2026-10-20) by ClinVar-GKM ADR 0009; the choice itself stays open.**

As first written: for the weekly Parquet dataset, either (a) replay the published monthly full + deltas
(recommended: the published Parquet is then provably rebuildable from published bundles, by the same command a
user runs), or (b) assemble an unpublished full bundle for the newest weekly dataset and build from it, as the
1.1.0 runbook does once for its reference full (no replay, but an assembly of about 1.5–2.5 h per week, per
ClinVar-GKM plan #155 §6.6, and a build input users can't get). (a) depended on D3.

**Resolved:**

- (a)'s dependency on D3 is gone (see D3). The replay start is now computable from published data, so (a) works
  as described, and `--release` can resolve it from the line index.

**Changed by ADR 0009, not decided:**

- ADR 0009 publishes a **weekly full** for every release in `v1/1.1/weekly/`. So (b) becomes (b'): build from the
  published weekly full of the newest release. That removes (b)'s two objections: the assembly is already done
  to publish the weekly full, and the input is a file users can download (until the month rolls over). The
  Parquet then comes from the exact bytes a user gets, with no weekly replay.

**Still open (the maintainer decides):** which input ClinVar-GKM's weekly Parquet build uses, (a) or (b').
Trade-off: (a) exercises the replay path users need for past weeks every week; (b') is simpler and faster and
doesn't depend on the delta chain. Either way the tool supports both, and the oracle (§8.2) builds both ways.
The earlier recommendation of (a) predates the weekly fulls and should be reconsidered.

### D3. The monthly full's source release isn't machine-readable

**Resolved (2026-10-20) by [ClinVar-GKM ADR 0009](https://github.com/clingen-data-model/clinvar-gkm/blob/docs/adr-0008-bundle-record/docs/decisions/0009-r2-layout-mirrors-ncbi-clinvar.md)**
(proposed, on PR #168, not merged yet).

As first written (**user, ClinVar-GKM change**): every live delta manifest names the same `checkpoint_full`
(§4.3), so the replay start can't be derived. Recommended: ClinVar-GKM records `source_release` for each monthly
full in the index and in each delta manifest's `checkpoint_full` (`{path, release, source_release}`), with
correct `checkpoint_full` values. Until then the tool takes `--full-source-release`, and `--release latest` is
unavailable. Also fix the docs replay example.

What ADR 0009 decides:

- **Adopted:** the line index publishes each official monthly's `source_release` (and `sha256`).
- **Adopted:** each delta manifest's `checkpoint_full` names the official monthly that **precedes** the delta,
  not the newest one.
- **Adopted:** the replay rule (§4.3): the newest monthly whose `source_release` ≤ W, then the deltas after it up
  to W, with the chain check.
- **Not adopted, not needed:** `source_release` inside `checkpoint_full`. The tool reads it from the line index
  by the monthly's release.
- **Docs replay example:** ADR 0009 records the defect; fixing the page is ClinVar-GKM's docs work, tracked
  there, not a decision here.

For the tool: `--release` works from the line index; `--full-source-release` stays only as an override for a
local full the index can't name. Until the 1.1.0 data is live, the corrected manifests and the index field are
not verified (§15).

### D4. Is the one-record-per-line layout a contract?

**user (ClinVar-GKM).** The tool's reader depends on the assembler's layout (§4.2). Recommended: ClinVar-GKM
documents it as a stable property of published bundles (in the release-model docs or an ADR), and a layout
change becomes a bundle-version event. Fallback if not: the tool adds a slow general streaming JSON parser
(e.g. `ijson`) for bundles that don't match.

### D5. Who owns column descriptions

**user.** Names and types: the spec here is authoritative (recommended). Descriptions: either keep them in
ClinVar-GKM `tables.md` (teaching prose, as now) and link to the spec for names and types (recommended for
spec 1.0), or move them into the spec and generate the docs table. Either way one source, the other links.

### D6. Tag format

**default.** `vX.Y.Z` for tool tags, to distinguish from bundle schema tags (`1.1.0`).

### D7. Archived 1.0.x bundles

**user.** Recommended: v1 does not read 1.0.x bundles (the frozen line `v1/1.0/`). 1.0.1 has a different
section and table layout (`varcond-proposition`, …), and there were no complete full-bundle downloads in the
measured window (ClinVar-GKM ADR 0008). Supporting it later would mean a separate spec (the 1.0.1 layout) and is
possible if asked for.

Note (2026-10-20): this plan first said the archive would keep the BigQuery-built 1.0.1 Parquet set. ClinVar-GKM
ADR 0009 reverses that: `v1/1.0/` has no Parquet. Once the old Parquet trees are deleted, no 1.0.1 Parquet is
published anywhere, and this recommendation means nobody can get one. The maintainer should confirm that is
acceptable.

### D8. Pin DuckDB exactly

**default.** Pin `duckdb==<x.y.z>` per release for byte-reproducible output, and recommend `uvx`/`pipx`.
Trade-off: a library user's own DuckDB may conflict; the tool is a CLI first.

### D9. Where the oracle and the release build run

**user.** About 50 GB free disk and 16 GB RAM are recommended (§6.3); the workstation and the build machine have
about 14–15 GB free. Options: a short-lived cloud VM, ClinVar-GKM's Cloud Run job with an attached disk, or
freeing space locally. Recommended: a VM for the oracle now; decide the release-build host in rollout step 3.

### D10. Compression and sort order for the core tables

**default for spec 1.0:** Snappy and default row groups (parity with today), sorted by id. **user, later:** ZSTD
would shrink the set (PR #151 measured 189 MB with ZSTD vs 328 MB with Snappy on one lookup file) but changes
download sizes and remote-query cost; decide after the oracle passes. Writer settings aren't part of the spec's
schema, so this needs no spec MAJOR.

### D11. Unsupported `schema_version`: refuse, with no override

**default.** Refuse. An override flag (`--force-schema-version`) would let users try a newer bundle but produce
files whose correctness nobody checked. Revisit if users ask.

### D12. ClinVar-GKM ADR amendments

**user (ClinVar-GKM).** ADR 0007 Workstream 1 recommends Parquet from assembler NDJSON (its option A); this tool
builds from the bundle (option B), per ADR 0001 here. That amendment is still needed.

The ADR 0008 (e) part is settled (2026-10-20): ADR 0009 amends ADR 0008 (e) to one Parquet dataset at
`v1/1.1/parquet/`, overwritten every release, no Parquet in archives or frozen lines, and this tool as the
rebuild method (both on PR #168, not merged yet). This plan follows it.

### D13. First tool release that ClinVar-GKM pins

**default.** 1.0.0, cut only after the oracle passes; 0.x before that.

### D14. Keep the 1.1.0 oracle reference

**user (ClinVar-GKM operations).** The runbook stages the 2026-10-18 BigQuery Parquet set (about 12 GB) and the
reference 2026-10-18 full (about 4.9 GB) in local staging, which is short on disk and gets cleaned. Recommended:
before cleanup, copy both with a sha256 list to a private location (for example `gs://clinvar-gkm/`, not the
public R2 bucket), so the oracle can run later on a larger machine. Without it, the oracle waits for a later
weekly release and needs its own frozen copy.

### Risks

| Risk | Effect | Mitigation |
| --- | --- | --- |
| The 1.1.0 latest set isn't published yet | Spec 1.0 and the oracle wait for it | Build v0 against the docs and SQL; capture the spec from the export when it lands (§3.2) |
| BigQuery typed columns hold values the bundle doesn't (all-null structs, `[]` vs NULL, `[{}]`) | Oracle differences that aren't tool bugs | Classify each in the report; the tool follows the bundle (ADR 0001); maintainer signs off |
| The oracle reference is overwritten weekly | Nothing to compare against | Freeze a copy with sha256s at the 1.1.0 publish (§8.2) |
| A new extension name, section or field appears in a bundle | Silent loss | Fail loudly; a new `schema_version` needs a tool release anyway |
| DuckDB casting differs from BigQuery (struct field order, integer widths, `DATE`) | Schema mismatch | Explicit types from the spec; `DESCRIBE` check on every build |
| Build time and disk higher than estimated | Weekly release slower | Measure in v0 (§12 step 1); subset builds; run on a larger machine (D9) |
| CDN limits (250 requests per 10 s) and the path allowlist | 429s or 403s for users | Single-stream downloads, backoff, `Range` resume; only read `/v1/` and `/index.json` (`/archive/` is dropped from the allowlist once `archive/1.0.1/` moves to `v1/1.0/`) |
| Published paths move at month and year rollover, and weekly fulls are deleted (ClinVar-GKM ADR 0009) | A hard-coded URL breaks; a weekly full is gone after its month | Resolve every input by release through the line index (§4.1); rebuild a past week from a monthly plus deltas (§4.3) |
| Two version numbers confuse users | Wrong tool for a bundle | `v`-prefixed tags; the refusal message names the matrix; metadata in every file |
